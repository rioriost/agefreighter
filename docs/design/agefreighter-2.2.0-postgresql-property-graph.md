# AGEFreighter 2.2.0 PostgreSQL property graph target plan

**Status:** Reviewed; Phases A and B complete on branch `2.2.0`
**Target release:** AGEFreighter 2.2.0
**Feature maturity:** Experimental while PostgreSQL 19 is pre-release
**Reviewed:** 2026-09-03

## 1. Objective

Add PostgreSQL 19 SQL/PGQ property graphs as a second migration target without
changing the existing Apache AGE target contract. AGEFreighter will load graph
records into ordinary PostgreSQL tables, declare those tables as a property
graph, and prove that the result is queryable through `GRAPH_TABLE`.

This is a new target, not an AGE compatibility mode. Apache AGE stores graph
objects in AGE-managed relations and is queried with Cypher. PostgreSQL 19
property graphs are read-only graph views over user-owned relational tables and
are queried with SQL/PGQ. Treating one as the other would make lifecycle,
metadata, and verification behavior unsafe.

## 2. Validated development baseline

The initial implementation is qualified locally with Apple Container 1.0.0 on
Apple Silicon and the official multi-platform PostgreSQL image:

```text
docker.io/library/postgres:19beta3@sha256:a48b19841e04b35b72a25e9a94314ac80546d32b5e2e3cd9279390cbd8a99572
arm64 manifest: sha256:d2803db84af749f279166b231e05a92c7d5ef991540cb292a76fb41af997ebd4
server: PostgreSQL 19beta3 (Debian 19~beta3-1.pgdg13+1)
server_version_num: 190000
```

The following behavior was exercised before this plan was reviewed:

- `CREATE PROPERTY GRAPH` accepts vertex and edge tables with explicit source
  and destination keys.
- `GRAPH_TABLE` returns the expected directed match and projected properties.
- A property graph appears in `pg_class` with `relkind = 'g'`.
- The graph definition is schema-qualified, but its table references must be
  resolved using a controlled `search_path`; schema-qualified names are not
  accepted after `REFERENCES` in the tested beta syntax.
- The image contains both amd64 and arm64 Linux variants. Apple Container runs
  the arm64 variant natively.

The tag is convenient for discovering newer PostgreSQL 19 development builds,
but all repeatable tests must record and run a resolved digest. A digest update
is a reviewed compatibility change.

## 3. User-visible contract

The target discriminator is:

```yaml
target:
  type: postgresql-property-graph
  graph: supply_chain
  schema: public
  mode: create
  connection:
    env: AGEFREIGHTER_TARGET_DSN
  propertyMode: replace
```

Rules for the first complete slice:

- PostgreSQL 19 or newer and working SQL/PGQ DDL are mandatory.
- `schema` defaults to `public` and is emitted in static plans.
- `graph` and `schema` are PostgreSQL identifiers, not AGE graph names.
- `create` is the first supported mode. `replace`, `append`, and `upsert` are
  enabled only after their lifecycle and recovery suites pass.
- Existing `apache-age` configurations and outputs remain byte-compatible
  except where a schema field is intentionally added to the target plan.
- The feature is documented as experimental until PostgreSQL 19 GA is tested.

## 4. Storage and query model

### 4.1 Tables

Each source vertex label maps to one vertex table and each edge label maps to
one edge table in the configured schema. Physical names are deterministic,
PostgreSQL-safe, collision-checked names derived from the logical label.

Vertex tables contain:

| Column | Type | Purpose |
| --- | --- | --- |
| `id` | `bigint generated by default as identity` | SQL/PGQ element key |
| `source_namespace` | `text` | source identity namespace |
| `external_id` | `text` | stable source identity |
| `properties` | `jsonb` | lossless dynamic property bag |

The pair `(source_namespace, external_id)` is unique.

Edge tables contain their own stable identity, `start_id` and `end_id` foreign
keys, and `properties jsonb`. Mappings must identify the endpoint vertex labels
before DDL is created. Tables and graph objects are owned by the migration
role; AGE catalogs and AGE graph IDs are never used.

### 4.2 Property exposure

The initial graph exposes stable identity fields and the full `properties`
JSONB value. Arbitrary Neo4j, CSV, PostgreSQL, or Cosmos property keys remain
lossless, but they are not automatically promoted to statically named SQL/PGQ
properties. Optional typed property projection is deferred until its schema
evolution and type-conflict rules are designed.

### 4.3 Transactions and metadata

The generic pipeline and `internal/sink` transaction interface remain shared.
A new `internal/pggraph` implementation owns PostgreSQL property-graph DDL,
table writes, capability probing, naming, lifecycle, and verification.

The current metadata schema encodes AGE relation OIDs, label IDs, and graph ID
allocation. PostgreSQL property graphs must therefore use backend-neutral job,
batch, checkpoint, rejection, and source-fingerprint records, plus a dedicated
table-generation mapping. AGE-specific generation columns stay valid for AGE;
they are not populated with synthetic PostgreSQL values.

## 5. Implementation sequence

### Phase A: capability and contract foundation

- add `postgresql-property-graph` to the typed config and JSON Schema
- add target `schema`, defaulting and target-specific validation
- emit the schema in `plan` output
- add a PostgreSQL 19 capability probe with explicit version and feature errors
- add identifier quoting, deterministic physical names, and pure DDL builders
- add unit, fuzz, and Apple Container integration smoke tests

Exit gate: configuration and generated DDL round-trip against the pinned beta
image while all existing AGE tests remain green.

### Phase B: backend-neutral orchestration

- introduce a target adapter boundary in `internal/app`
- move AGE construction behind that boundary without behavior changes
- add backend-neutral lifecycle and metadata interfaces
- migrate metadata to a new schema version with explicit backend identity
- prove old v17 AGE jobs upgrade and resume unchanged

Exit gate: the AGE integration and recovery matrices pass through the new
boundary, and no PostgreSQL property-graph code imports `internal/age`.

### Phase C: transactional create loads

- create schemas, vertex tables, edge tables, constraints, and property graph
- implement ordered vertex and edge batch writes
- resolve edge endpoints with bounded memory
- commit metadata checkpoints atomically with each batch
- support explicit resume of interrupted create loads
- finalize only after row-count and graph-query checks pass

Exit gate: every existing source connector completes a create migration into
PostgreSQL 19 with deterministic report and checkpoint output.

### Phase D: verification and diagnostics

- compare counts by label and relationship type
- verify missing endpoints, uniqueness, foreign keys, and rejected records
- query representative directed and undirected patterns through `GRAPH_TABLE`
- add deterministic ranged digests over logical records
- extend `doctor`, `report`, and `verify` with backend-specific capabilities
- prove that source immutability and target digests survive recovery

Exit gate: corruption tests detect changed properties, identities, and endpoint
bindings; full digest roots match after clean and recovered runs.

### Phase E: remaining modes and release hardening

- design and implement atomic `replace`
- implement `append` duplicate policies and `upsert` property modes
- add concurrency and interrupted-finalization tests
- benchmark small, medium, and production-scale workloads
- qualify the newest PostgreSQL 19 development digest, then PostgreSQL 19 GA
- update compatibility, configuration, installation, operations, and roadmap

Exit gate: release checks, mode matrix, recovery suite, security review, and
documentation are complete. Unsupported modes continue to fail validation.

## 6. Test plan

### 6.1 Unit and contract tests

- target discriminator, defaults, identifier limits, and invalid combinations
- JSON Schema and Go parser acceptance/rejection parity
- SQL identifier quoting, reserved words, Unicode, truncation, and collisions
- deterministic table-name and DDL golden tests
- PostgreSQL version parsing and capability diagnostics
- dependency boundary: source packages cannot import either target adapter
- property JSON canonicalization and null/type round trips

### 6.2 Apple Container integration

A repository script will manage only the dedicated
`agefreighter-pg19-sqlpgq` container. It will never reset or remove unrelated
containers. The script will:

1. verify Apple Container is available and running;
2. pull or select a configured PostgreSQL 19 image by digest;
3. wait for readiness and record exact server/image versions;
4. run the adapter integration suite using
   `AGEFREIGHTER_PGGRAPH_TEST_DSN`;
5. retain logs on failure and stop the dedicated container on request.

The integration suite covers DDL creation, `relkind = 'g'`, directed
`GRAPH_TABLE` matching, JSONB property projection, rollback, cleanup, and
unsupported PostgreSQL 18 rejection.

### 6.3 End-to-end source matrix

For CSV, PostgreSQL, Neo4j 4.4, Neo4j 5.26, and Cosmos fixtures:

- empty graph; vertices only; mixed vertices and edges
- multiple vertex/edge labels and endpoint label pairs
- Unicode, large properties, numbers, booleans, nulls, arrays, and objects
- duplicate identities, missing endpoints, malformed records, quarantine
- bounded-memory loading and deterministic checkpoints
- clean run versus SIGTERM/resume digest equivalence

### 6.4 Regression and performance

- run the complete Apache AGE unit/integration/recovery matrix unchanged
- compare load throughput, transaction latency, target size, and verification
  time against the AGE target using the same corpus
- enforce the existing memory limit and detect unbounded endpoint caches
- perform an EXPLAIN-based review of endpoint lookups and digest scans

No production-scale claim is made from the local Apple Container smoke test.
That claim requires a separately budgeted environment and retained evidence.

## 7. Release acceptance criteria

- PostgreSQL 19 GA is available and passes the full suite, or 2.2.0 explicitly
  ships the target as experimental with a pinned supported pre-release build.
- All advertised load modes pass clean and two-fault recovery runs.
- Source and target canonical digests match for every supported source.
- No literal credentials, connection strings, or local paths enter artifacts.
- Existing Apache AGE compatibility and release gates remain green.
- Compatibility documentation distinguishes SQL/PGQ from Cypher and describes
  JSONB property access accurately.
- The official development image digest, server build, architecture, and Apple
  Container version are recorded for every qualification run.

## 8. Design review record

The plan was reviewed against the current config, app, AGE adapter, sink, and
metadata boundaries. The following changes were made during review:

1. **Separate target selected.** Reusing the AGE adapter was rejected because
   PostgreSQL property graphs do not provide AGE catalogs, labels, graph IDs,
   or Cypher semantics.
2. **Lossless JSONB first.** Automatic typed property promotion was removed
   from the initial scope because SQL/PGQ property names are static while
   source property bags are dynamic and may contain conflicting types.
3. **Create mode first.** Advertising all existing modes before lifecycle and
   recovery tests was rejected. Each mode is enabled only with evidence.
4. **Feature probe added.** A version-number check alone is insufficient for a
   development build; the adapter must also prove property-graph DDL support.
5. **Catalog coupling minimized.** Beta catalogs may change before GA. Public
   SQL and information-schema views are preferred; direct catalog reads are
   isolated and version-gated where unavoidable.
6. **Controlled search path required.** Live testing found that referenced
   tables in the graph declaration must be resolved in the target schema.
   Generated transactions set a local, quoted `search_path` and never inherit
   an untrusted caller search path.
7. **Digest pinning required.** A moving development tag is useful for update
   discovery but cannot be the qualification identity.
8. **AGE regression is a release blocker.** Target construction and lifecycle
   must remain behind the backend boundary, and that boundary must preserve
   existing AGE behavior before PostgreSQL property-graph loads are wired into
   it.

No unresolved design blocker prevents Phase C from starting. PostgreSQL
property-graph transaction and lifecycle semantics remain the next dedicated
review point before its load path is enabled.

## 9. Current implementation status

Phase A completed on 2026-09-03. The target discriminator and schema contract,
target-specific validation, static-plan output, safe naming and quoting, pure
relational/property-graph DDL generation, server/feature probe, and the pinned
Apple Container integration harness are implemented. The Beta 3 integration
test creates a directed graph, round-trips a JSONB property through
`GRAPH_TABLE`, and confirms property-graph `relkind = 'g'`.

Phase B completed on 2026-09-03. Target selection, session lifecycle, metadata
inspection, and metadata migration now enter through `internal/target`;
Apache AGE construction is behind that boundary. AGE-only operations are
requested through an explicit capability check, so an implemented non-AGE
runtime cannot accidentally be treated as AGE. Degraded diagnostics validate
the target backend before resolving or opening its connection. PostgreSQL
property-graph operations remain fail-closed with an explicit
unsupported-adapter error until Phase C installs its runtime.

Metadata schema v18 records the target backend and schema on every job. Reads
remain compatible with v14-v17 metadata by interpreting missing target
identity as Apache AGE, while the v18 migration permanently backfills that
identity and removes insertion defaults. Status, report, verification, resume,
and replacement cleanup reject a job whose stored target identity differs from
the supplied configuration. The v14-v17-v18 integration fixture proves an
existing failed AGE job can be read before migration, upgraded, and returned
to running state unchanged, and that a PostgreSQL property-graph job
round-trips its explicit backend identity.

The full unit and race suites, release self-check, live AGE adapter/app suites,
and the complete AGE recovery matrix pass through the new boundary. The
PostgreSQL 19 Beta 3 container also passes the v14-v17-v18 metadata-upgrade
fixture. The PostgreSQL property-graph package is protected by an architecture
test that rejects any dependency on `internal/age`. Transactional PostgreSQL
property-graph create operations are intentionally not part of Phase B; Phase
C will add them behind the completed runtime boundary.

The repository-wide coverage gate is 88.8% with the AGE integration DSN,
against a required 90.0%. Phase A measured 88.9%, so this is a pre-existing
release-gate deficit rather than a Phase B regression. The threshold has not
been weakened and must be restored before the 2.2.0 release criteria are
declared complete.
