native-interaction evidence. Historical September windows remain expired.

## Production correction and local evidence

`runnerResize.ts` now checks `assessmentActive(record)` before initial or
retained resize operations. A completed ARM Run Command can have launched a
still-running asynchronous inventory/catalog worker; checking only the command
receipt missed that state. All unresolved assessment/catalog states now stop
before ARM access, persistence, deallocation, size changes, or restart.

The focused resize suite has 38 passing cases, including 15 new regressions:
14 unresolved worker cases exercise the initial path and every retained resize
phase with and without approval; one positive case preserves successful sealed
inventory/catalog behavior. These are inert-adapter unit results, not live
refusal evidence. The independent B06 agent reviewed the change and reported
no requested correction.

## Dedicated resource prerequisites

Use a newly created zonal workflow-owned runner with persistent OS disk, one
NIC, system identity and current matching Linux readiness. The initial size
can be `Standard_B2s_v2`; the reviewed migration size is `Standard_D4s_v5`.
The real workflow must retain its own actual complete source inventory and
hash-verified imported report before target creation. No reused target record,
foreign accepted workflow, fabricated seal or synthetic `provisioned` phase.

The minimum target options offered by the current GUI are PostgreSQL 18,
`Standard_D4ds_v5`, GeneralPurpose, 128 GiB, HA disabled and public access
disabled. The target uses the same region and zone as its runner. The default
server name is `afpg-` plus the first 20 compact workflow UUID characters;
it must be a new globally available name. The delegated subnet is newly
created inside the selected existing VNet and must be non-overlapping
(canonical IPv4 /8 through /28). Private DNS and the VNet link are newly
workflow owned. Server, database, AGE allow-list and preload are reconciled
by the ordinary target controller until `provisioned` is genuinely observed.
Use current quoted prices and the newly approved deadline/reserve/ceiling;
this document does not fix a price or extend a window.

it. Both source panels must be genuinely reviewed before target creation;
synthetic review state or script-posted messages do not qualify GUI acceptance.

## Optional read-only controls and coverage limits

The normal runner panel's **Check Linux guest readiness** creates a real
pending guest command and can establish the pending-control denial. It does
not establish an active migration or asynchronous source worker.

The selected second-inventory route tests an active source worker without
starting a load: after the first report import, review the unchanged source again BEFORE
target creation, keep that source panel open, and only then invoke its normal
inventory approval after the target is provisioned. Closing/reopening the
panel clears in-window review; target-existing workflows cannot re-review
source configuration. This route must retain actual running guest-worker
proof, and still qualifies an active inventory rather than an active load.

Neither a normal host with synthetic prerequisites nor an inert GET response
qualifies these live gates. No budgeted cloud operation or actual GUI trial
was performed while preparing this plan.
